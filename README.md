# cue-vision

Сервис приёма событий детектора [snooker_CV](https://github.com/TechnoCheese/snooker_CV)
и статистики тренировок. Go + PostgreSQL.

Детектор смотрит на стол и выдаёт поток событий: удар кием, соударения, борта, лузы
(`docs/EVENTS.md` в его репозитории, схема `0.1`). Сервис этот поток принимает, собирает
из него удары, относит их к тренировкам и отвечает на вопросы «сколько забил», «какая
реализация», «куда мажет».

## Быстрый старт

```
docker compose up -d --build
```

Сервис слушает `:8080`, база — `127.0.0.1:5433`. Миграции применяются при старте.

Загрузить запись детектора и посмотреть статистику:

```
curl -X POST 'http://localhost:8080/api/v1/events?stream=club1-t1' --data-binary @testdata/session_100s.jsonl
curl 'http://localhost:8080/api/v1/trainings?stream=club1-t1'
curl 'http://localhost:8080/api/v1/trainings/1/stats'
```

## Как события попадают в сервис

**Поток** (`stream`) — один экземпляр детектора над одним столом, например `club1-t1`.
Имя потока задаёт отправитель; по нему сервис отличает столы друг от друга.

1. **Файл или пачка по HTTP.** `POST /api/v1/events?stream=<поток>` с телом в JSON Lines,
   как его пишет `snooker_cv run --events`, либо JSON-массивом событий. Тело можно сжать
   (`Content-Encoding: gzip`). Пачки одного потока можно слать по частям и повторять.

2. **Живой детектор по WebSocket.** Детектор с ключом `--ws` сам является сервером;
   сервис подключается к нему клиентом и переподключается после обрыва:

   ```
   python -m snooker_cv run rtsp://cam-3/stream --config halls/club1.yaml --ws ws://0.0.0.0:8765
   DETECTORS=club1-t1=ws://192.168.1.20:8765 docker compose up -d
   ```

   Для детектора на той же машине, что и compose, адрес — `ws://host.docker.internal:8765`
   (детектор при этом должен слушать не только `127.0.0.1`).

3. **Проигрывание записи** — тем же путём, что и живой детектор:

   ```
   python -m snooker_cv replay out/session.jsonl --ws ws://0.0.0.0:8765
   ```

По тому же соединению сервис передаёт детектору команды (`EVENTS.md` §7.1): заказ шара и
лузы на удар, режим, перезасев раскладки, перекалибровку.

```
curl -X POST http://localhost:8080/api/v1/detectors/club1-t1/commands \
     -d '{"cmd":"set_target","ball":"red_03","pocket":"tr"}'
```

## Тренировки

Тренировка — окно времени на потоке. Удар относится к тренировке, если **момент начала
удара** попадает в `[started_at, ended_at)`. Решает время удара, а не время доставки:
подтверждённые события детектора отстают от камеры примерно на 4.3 с, и удар, сделанный
за секунду до конца тренировки, придёт уже после её закрытия — и всё равно в неё попадёт.

```
curl -X POST http://localhost:8080/api/v1/players   -d '{"name":"Иван Петров"}'
curl -X POST http://localhost:8080/api/v1/trainings -d '{"stream":"club1-t1","player_id":1,"title":"Дальние удары"}'
# ... игрок тренируется ...
curl -X POST http://localhost:8080/api/v1/trainings/1/finish
curl http://localhost:8080/api/v1/trainings/1/stats
curl 'http://localhost:8080/api/v1/players/1/stats?from=2026-11-01&tz=Europe/Moscow'
```

Тренировку можно открыть и закрыть задним числом (`started_at`, `ended_at`): уже принятые
удары перейдут в неё и выйдут из неё по тому же правилу окна. Для записи, проигрываемой
через `replay`, правило работает на скорости 1 — иначе время записи расходится с часами.

Открытая вручную тренировка на потоке может быть только одна. Удары вне такой тренировки
собираются в **автоматическую** (`origin: "auto"`): она открывается первым ударом и
закрывается вместе с сессией детектора либо когда на потоке открывают тренировку вручную.
Поэтому загруженный файл сразу даёт тренировку со статистикой; приписать её игроку можно
задним числом: `PATCH /api/v1/trainings/{id}` с `{"player_id": 1}`. Автоматические
тренировки отключаются настройкой `AUTO_TRAINING=false`.

## Статистика

Считается по завершённым ударам (есть `shot_end`) в момент запроса. Доступна по тренировке,
по сессии детектора и по игроку за период.

Исход удара — один из четырёх, `shots = pots + misses + no_contact + in_offs`:

| Исход | Условие |
|---|---|
| `pot` | упал прицельный шар, биток остался на столе |
| `in_off` | биток упал в лузу (что бы ни упало вместе с ним) |
| `no_contact` | биток не коснулся ни одного шара и ничего не упало |
| `miss` | всё остальное: касание было, результата нет |

Если детектору был передан заказ (`declared_target` в `shot_end`), `pot` засчитывается
только за заказанный шар и, когда луза названа, только в неё. Без заказа — за любой
прицельный шар: ядро не знает, что игрок задумал. Биток удара — шар из `cue_strike`;
в снукере (`game: "snooker"` в `session_start`) — всегда белый (`white` / `white_NN`).
Если детектор открыл снукерный удар по цветному шару (шар катнул помощник или детектор
упустил размытый белый), сервис смотрит события удара: тронулся белый — удар
пересчитывается от него (первый контакт — первое столкновение белого, геометрия и
`near_miss` детектора отбрасываются); не тронулся — удар помечается `rejected` с
причиной в `reject_reason` и в статистику не идёт.

Детектор сообщает, что тронуло шар (`cause` в `ball_start`: `cue`, `hand`, `ball`,
`unknown`), но не решает, удар ли это. Решает сервис: в снукере белый, которого двигала
только рука, — не удар игрока (раскладка, поправка битка ладонью). `hand` у детектора
значит, что шар несли, а не били: с ним ехала ладонь или кий, который рука вела вместе
с шаром, не отрывая (подробно — EVENTS.md детектора, §4.2). Такой удар —
открыт ли он по белому или по цветному — помечается `rejected` с причиной «биток двигала
только рука», если одновременно:

- у белого в ударе есть хотя бы один `ball_start` с `cause: "hand"`;
- нет ни одного собственного старта белого с другой причиной. Отскок — старт белого
  сразу после его столкновения, без `ball_stop` между ними, — собственным не считается:
  белый, которого ладонью толкнули в другой шар, остаётся толкнутым рукой;
- нет улики кия: ни старта белого с `cause: "cue"`, ни `cue_strike` по белому с
  `source: "cue"`.

`unknown` и отсутствие поля (старые детекторы) рукой не считаются: при сомнении удар
остаётся. Если белый сначала двигала рука, а потом он ушёл от кия или по неизвестной
причине, биток удара считается от этого второго старта: место и скорость — из него,
первый контакт — первое столкновение белого после него.

| Поле | Смысл |
|---|---|
| `pot_rate` | `pots / shots`; `null`, когда ударов нет |
| `balls_potted` | упавшие прицельные шары (один удар может дать несколько) |
| `best_streak` | самая длинная серия результативных ударов подряд в одной тренировке |
| `near_misses`, `near_miss_left`, `near_miss_right` | прицельный прошёл рядом с лузой и не упал; с какой стороны от линии на лузу — ответ на «мажет вправо в X из Y» |
| `avg_cue_speed`, `max_cue_speed` | скорость битка после удара, длин стола в секунду |
| `avg_cut_angle` | средний угол резки, градусы |
| `avg_cue_to_object`, `avg_object_to_pocket` | дистанции биток → прицельный и прицельный → луза, в долях длины стола |
| `by_pocket` | падения и близкие промахи по лузам (`tl tm tr bl bm br`) |
| `by_ball` | забитые шары по цветам |
| `by_cut_angle` | результативность по углу резки: 0–15, 15–30, 30–45, 45–60, 60–90° |
| `by_distance` | результативность по дистанции до прицельного: до 0.25, до 0.5, дальше |
| `warnings` | предупреждения детектора по кодам (только у сессии) — мера доверия к данным |

Расстояния и скорости — в нормированных единицах потока, как их даёт детектор.

## API

Все пути — под `/api/v1`. Ответы — JSON, время — UTC в RFC 3339, списки — `{"items": [...]}`
с параметрами `limit` и `offset`. Ошибка — `{"error": "..."}` с кодом 4xx или 5xx.
Если задан `API_TOKEN`, нужен заголовок `Authorization: Bearer <токен>`.

| Метод и путь | Назначение |
|---|---|
| `POST /events?stream=` | принять события; ответ — сколько принято, сколько дублей, какие строки отвергнуты |
| `GET /sessions?stream=&status=` | сессии детектора |
| `GET /sessions/{id}` | сессия с калибровкой стола и итогом прогона |
| `GET /sessions/{id}/stats` | статистика сессии |
| `GET /sessions/{id}/shots` | удары сессии |
| `GET /sessions/{id}/events?type=&after_id=&limit=` | сырые события в порядке приёма |
| `POST /sessions/{id}/close` | закрыть сессию, оставшуюся без `session_end` |
| `POST /trainings` | открыть тренировку: `stream`, `player_id`, `title`, `exercise`, `notes`, `started_at` |
| `GET /trainings?stream=&player_id=&status=` | тренировки |
| `GET /trainings/{id}` | тренировка |
| `PATCH /trainings/{id}` | изменить `player_id`, `title`, `exercise`, `notes`; `null` очищает поле |
| `POST /trainings/{id}/finish` | закрыть тренировку; необязательное `ended_at` |
| `GET /trainings/{id}/stats` | статистика тренировки |
| `GET /trainings/{id}/shots` | удары тренировки |
| `GET /shots/{id}` | удар с падениями и событиями, из которых он сложился |
| `POST /players` | завести игрока: `name` |
| `GET /players`, `GET /players/{id}` | игроки |
| `GET /players/{id}/stats?from=&to=&tz=` | сводка по тренировкам игрока за период и разбивка по дням |
| `GET /detectors` | состояние подключений к детекторам |
| `POST /detectors/{stream}/commands` | команда детектору: `set_target`, `set_mode`, `reset_layout`, `recalibrate` |

Вне `/api/v1`: `GET /healthz` — процесс жив, `GET /readyz` — база доступна.

## Как устроена обработка

**Сессия** — прогон детектора от `session_start` до `session_end`. Новая шапка на том же
потоке закрывает прежнюю сессию как прерванную. События, пришедшие без шапки, попадают в
активную сессию потока, а если её нет — в неявную (`implicit: true`).

**Время.** Событие несёт `t` — секунды от начала сессии; абсолютное время равно
`origin_at + t`. Началом служит `started_at` из шапки. Исключения — поток без шапки и
запись, проигранная по WebSocket (`source_kind: "replay"`): у них шкала начинается в
момент получения, потому что `started_at` в записи остался от исходного прогона.

**Идемпотентность.** Каждое событие сохраняется в `events` с отпечатком содержимого, и
производные записи строятся только для события, которого там ещё не было. Файл можно
загрузить повторно, пачку — повторить после сбоя с любого места: ничего не удвоится.
Сессия при повторной загрузке узнаётся по потоку и `started_at`.

**Порядок.** Подтверждённые события детектор выдаёт строго по `t`, служебные и
диагностические (`delivery: "immediate"`) их обгоняют. Удар собирается только из
подтверждённых: `shot_start` открывает его, первый `cue_strike` даёт биток, `shot_end`
закрывает и приносит сводку. Удар без `shot_end` (детектор перезапустился посреди удара)
помечается `aborted` и в статистику не идёт. Удар, который сервис не признал игровым
(см. «Статистика»), помечается `rejected`; он тоже остаётся в базе вместе с событиями.

**Совместимость.** Незнакомые типы событий и поля не отвергаются, а сохраняются как есть —
этого требует контракт потока (§6.6). Покадровые `positions` по умолчанию не сохраняются
(`SKIP_EVENT_TYPES`): это 25 событий в секунду, и статистике они не нужны.

Таблицы: `sessions`, `trainings`, `players`, `shots`, `pots` (падения с лузой и скоростью
входа), `events` (сырой поток). Схема — `internal/store/migrations`.

## Настройки

Переменные окружения, см. `.env.example`.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `HTTP_ADDR` | `:8080` | адрес HTTP-сервера |
| `DATABASE_URL` | `postgres://cuevision:cuevision@localhost:5432/cuevision?sslmode=disable` | PostgreSQL |
| `API_TOKEN` | пусто | токен доступа к `/api/`; пусто — без проверки |
| `DETECTORS` | пусто | детекторы: `поток=ws://host:port` через запятую |
| `AUTO_TRAINING` | `true` | собирать удары вне ручных тренировок в автоматические |
| `SKIP_EVENT_TYPES` | `positions` | типы событий, которые не сохраняются |
| `MAX_BODY_BYTES` | `67108864` | предел тела `POST /events` (и распакованного объёма) |
| `DETECTOR_IDLE_TIMEOUT` | `60s` | тишина от детектора, после которой соединение считается мёртвым |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |

## Разработка

Нужен Go 1.25+. Тесты с базой включаются переменной `TEST_DATABASE_URL` и без неё
пропускаются; каждый такой тест работает в собственной схеме и чужих данных не трогает.

```
make test-db      # отдельный PostgreSQL на 127.0.0.1:55432
make test
make test-db-down
```

В `testdata/` лежат настоящие записи детектора: `session_100s.jsonl` (5 ударов, с шапкой
и `session_end`) и `bench_6reds_noheader.jsonl` (7 ударов, без шапки). Ожидаемые числа в
тестах сверены с разбором этих записей по кадрам.

| Каталог | Ответственность |
|---|---|
| `cmd/cue-vision` | точка входа |
| `internal/event` | разбор потока: общие поля, типы, отпечаток события |
| `internal/ingest` | события → сессии, удары, падения; оценка исхода удара |
| `internal/store` | PostgreSQL: миграции, тренировки, игроки, статистика |
| `internal/detector` | WebSocket-клиент детектора и обратный канал команд |
| `internal/api` | HTTP |

## Чего здесь нет

- Правил снукера и подсчёта очков: сервис не знает, чья очередь и какой шар «на игре».
- Определения игрока: детектор его не видит, тренировку приписывают игроку через API.
- Перевода в метры и м/с: детектор пока не сообщает физический размер стола.
